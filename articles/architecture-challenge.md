## Architecture Challengeとは
SRE・パブリッククラウド志望学生向けのインターンです。**複数のサービスを支えるマルチテナンシーなプラットフォームを設計せよ**というサブタイトルの通り、複数のテナントを動かす基盤を設計するというものでした。

> 1Dayでほぼ一日中インフラ（クラウド）の設計について考えることができました。脳みそいっぱい使いました！

## 参加者と筆者の技術力・経験
どんな人が参加しているのかな、ついていけるかな…と参加前は不安でしたが、話してみると以下のどれかの経験を持つ人が多かった印象です（あくまで筆者の観測範囲です）

- AWSなどのクラウドをバイトなどで触ったことがある
- 自宅サーバーを運用している
- セキュリティの知識がすごい

というように、基本的に何かしらの経験がある人が多く、話を聞いていて面白かったです。ちなみに筆者は自宅でk8sを運用して成果物を動かしている・ECSを使ったことがある程度のレベルでした。AWSの経験や自身でシステムのインフラを設計したことがあると、基本的な設計はかなりスムーズに進められると思います。

## 具体的な課題について
「複数ファンクラブサイトを統合的にホスティングするプラットフォームの設計」という題材でした。以下の点が特にポイントでした。

1. チケット購入などの急激なアクセス増加に対応できる
2. 複数のテナントで独立したファンクラブサイトをホスティングできる
3. 少数のプラットフォームメンバーでの開発、コスト最適化

個人的に戸惑ったのは、「想定するファンクラブサイトの構成概要は決まっているが、どこまでテナントを独立させるか」という点でした。マルチテナントという考え方自体に触れたことがなかった私にとっては、ここが一番難しかったです。

### アーキテクチャの要点

| レイヤー | 採用技術・方針 |
| --- | --- |
| CDN / WAF / 流量制御 | Cloudflare（CDN・WAF・Waiting Room） |
| コンピュート | EKS（Karpenterでインスタンスをスケール、HPAでPodをスケール） |
| オートスケーリング | Datadog Adapterでユーザー数などのカスタムメトリクスを取得し、HPAのトリガーに利用 |
| モニタリング | Datadog（Karpenter・HPAの稼働状況を含めて監視） |
| その他AWS | SQSで画像配信・メール送信などの非同期処理をキューイング |
| デリバリー | リポジトリ3つ＋ArgoCDによるGitOps |

**チケット購入などのスパイク対策**として、インスタンスレベルのスケーリングはKarpenter、Podレベルのスケーリングは通常のHPAに任せています。さらにDatadog Adapterを使い、CPU/メモリだけでなく「同時アクセスユーザー数」のようなアプリケーション側のカスタムメトリクスを取得してHPAのスケーリング判断に組み込んだのが工夫した点です。Karpenter・HPAの稼働状況自体もDatadogで一元的に監視できるようにしました。

Cloudflareは、CDN・WAF・Waiting Roomを組み合わせることで「アクセスに時間がかかる」「アクセスできない」という状況そのものを減らす狙いで採用しました。自宅サーバー運用でよく使っていて、コストパフォーマンスの良さを実感していたのも採用理由の一つです。

### 他の人と違う点
- **Cloudflareを使う**：自宅サーバーでよく使っており、CDN・WAF・Waiting Roomのコストパフォーマンスが良いと感じていたため採用
- **Datadog**：Prometheus + Grafanaでも良いのですが、SaaSに任せてその分の開発コストを別のところに割きたいと考えたため
- **開発フローから逆算した設計**：リポジトリが3つある想定で、開発者を何人ずつ振り分けてArgoCDを使うか、というところからシステム全体を考えました。実際に何度かk8sで開発していた経験があったからこそ、この発想になったのだと思います

具体的には、以下のようにチーム構成まで踏み込んで設計しました。

| チーム | 人数 |
| --- | --- |
| インフラ | 3名 |
| バックエンド（Terraformも書ける） | 3名 |
| バックエンド | 19名 |
| フロントエンド | 4名 |
| QA | 1名 |

インフラだけでなく「誰が何人でどのリポジトリ・レイヤーを開発するか」まで具体的に決めたことは、後述のメンターからのフィードバックでも評価されたポイントでした。

### EKSかECSか
他の参加者の発表を聞いていて非常に面白かったのが、コンピュート環境にECS（Elastic Container Service）を採用している人が多かった点です。

後々考えてみると、確かに「30個程度のファンクラブサイトを初期コストを抑えて立ち上げる」という要件を考えると、コストは最低限で十分ですし、最初からバズるようなことはないだろう、という意見にも納得感がありました。なるほど、スタートアップのビジネス的な視点もあるのだなと感じました。
一方私はというと、ECSもオンプレのk8sも使った経験から「Karpenter・ArgoCDを使いたい、使えばスパイク対応できるはず！」と考えていたので、「まずは小さく作る」という発想も新たに学ぶことができました。

## メンター・審査員からのフィードバック
発表後にいただいたフィードバックの中で印象的だったものを紹介します。

- **「EKSを選んだこと自体が難しい判断」という評価**：コスト・運用負荷の観点でECSが選ばれやすい中、EKSを選んだ理由（Karpenter・ArgoCDを活かしたスパイク対応）が明確だった点を評価してもらえました
- **「ArgoCDを使いたいからk8sを選ぶ、というのは珍しい」というコメント**：技術選定の起点が逆（k8sだからArgoCDではなく、ArgoCDを使いたいからk8s）だったのが珍しがられました
- **チーム構成まで具体的に決めた点は良かった**：インフラ3名・バックエンド（Terraform可）3名・バックエンド19名・フロントエンド4名・QA1名、という開発体制まで設計に含めたことを評価してもらえました
- **データ分離はschemaレベルで十分**：テナントごとのデータ分離は、必ずしもnamespace単位まで分けなくてもschema分離で問題ないとコメントをもらいました
- **フロントエンドの配信は改善余地あり**：これは参加者全員に共通する指摘だったようで、フロントエンドをEKS上に置いたままにしている設計は改善できるとのことでした

## 振り返り
- SQSは画像配信・メール送信などの非同期処理には使いましたが、一番スパイクが集中するはずの**チケット購入処理自体はWaiting Roomで流量を抑える方針に頼ってしまい、キューイングを組み込めませんでした**。ここはSQSを使うべき代表例だったと反省しています
- フロントエンドもEKSに置いているため、キャッシュが効かない・更新された直後などは毎回ALB・NATゲートウェイを通ってEKSまでアクセスが到達してしまいます。ここをうまくCloudflare側で配信できれば、さらに最適化できたはずです
- 「schemaでデータだけ分離して、あとはPodとインスタンスをうまくスケールすれば低コストで済む」と考えていましたが、namespaceで分離し、他のインフラもテナントごとに分離しているケースを見て、「巻き添えが起きず、費用の計算もしやすくなる」という別解があることを知りました
- 認証周りまで詳しく考えきれませんでした。マルチテナントにおける認証・認可は奥が深いです…

## まとめ
1Dayという短時間で「マルチテナント設計」というテーマに向き合ったことで、テナント間の分離度合いをどこまで踏み込むか、という設計判断の難しさと面白さを実感できました。技術選定だけでなく、開発体制やコストのバランスまで含めて設計する経験は、実務に近い形で学べる貴重な機会でした。次にマルチテナントの設計をする機会があれば、今回学んだnamespace分離や認証周りの考え方も取り入れてみたいと思います。
