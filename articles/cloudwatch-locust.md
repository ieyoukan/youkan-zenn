## 何が起こったのか

大学の講義が終わって、そろそろバイトの稼働を始めようかというタイミング。何気なくSlackを開いたら、共同開発先のチームチャンネルがざわついていました。

> 「aws cloudwatchがめっちゃ跳ねてる…」

![Cost Explorerのグラフ](/images/cloudwatch/graqh.png)
*(※青い部分がすべてCloudWatchの料金です)*

グラフを見た瞬間、「んんん!!??」と声が出ました。あ、これは絶対どこかのログが暴走してるやつだ、という嫌な予感がしました。そして、これが世に言う**CloudWatchのクラウド破産**か…とこの瞬間全てを察しました。講義終わりでバイト前だったのに、そのままバイトどころではなくなり緊急対応スタートです。

先方チームのチャンネルには、こんな感じでそのスレッドに返信しました。

> **私**: ログが制御できてないのは治さないとって思ってましたが酷すぎる...最優先で直します
> **私**:こういうコストの検知にこっち側からだと権限的にも気づけないのでどうにかしたいですね

実は当時、私にはAWSのBilling（コスト管理）権限が付与されておらず、自分からはコストの異変に気づけない状態でした。「権限がない」＝「破産する寸前まで気づけない」という、地味に一番怖いポイントです。この件をきっかけに、権限もその日のうちに付与してもらいました。

## 原因：大量のSocket.io通信 × DEBUGログ

案の定、先方に協力してもらってCost Explorerの内訳を確認したところ、CloudWatch Logsのデータ取り込み（Ingestion）料金だけが異常に跳ね上がっていました。
コストが急増したタイミング的にどう考えても...**開発環境で実施したLocustによる負荷試験**が真っ先に思いつきました。

### 原因となったアプリについて
私が開発しているのはメタバース的なアプリケーションで、ユーザーがアバターを動かしたり、アクションを起こしたりするたびに、裏側ではWebSocket（Socket.io）によるリアルタイム通信が頻繁に行われます。

### 負荷試験について
この負荷試験システム自体は私が作ったものでしたが、作った時点ではまだ本格的に動かしておらず、その後チームに新しく入った後輩のYさんに「これ使って負荷試験してレポート出してみて、あと落ちる原因も探ってみて」とチケットを切って渡していました。

当時の負荷試験の条件は以下の通りでした。

- **同時接続:** 最大70人〜100人のユーザー
- **アクション:** 全員が常にワールド内を歩き回り、座標データなどを送信し続ける
- **致命的な設定:** **ログレベルが `DEBUG` のままになっていた**

普段の開発時なら問題ないのですが、負荷試験中は「100人が毎秒動く座標データの通信」がすべてDEBUGログとして出力されていました。
CloudWatch Logsは「ログのデータ容量（GB）」に対して課金されます。結果として、数分ほどの負荷試験だったのに関わらず、ただ大量に動き続けるbotの座標データを吐き出すためだけに、毎日じわじわとコストが積み上がってしまいました。

## なぜ負荷試験システムを作ったときに気づかなかったか

負荷試験システムを作った時、私は「試験を実行する仕組み」のことしか考えていませんでした。コストの見積もりをしましたが、GitHub Actions・ECS・Lambda・CloudWatch……それぞれの料金体系を個別に見れば、実はどれも大した額にはならないはずだったのです。

| サービス | 料金体系 | 無料枠 | 今回のケースでの想定 |
| --- | --- | --- | --- |
| GitHub Actions | 実行時間（分）の従量課金 | プライベートリポジトリは月2,000分まで無料 | Locustのタスクを「起動するだけ」でジョブを終了させれば数十秒しか消費しない想定だった |
| Amazon ECS（EC2起動タイプ） | ECS自体は無料、EC2・EBSの料金がかかる | - | 既にEC2（t4g.smallなど）を開発環境として起動済みなら追加料金はないはずだった |
| AWS Lambda | リクエスト数＋実行時間（GB-秒） | 月100万リクエスト・40万GB-秒まで永久無料 | 試験完了時に1回動くだけなので実質無料の想定だった |
| CloudWatch Logs | データ取り込み量（GB）＋保存量（GB/月） | 取り込み5GB・保存5GBまで無料 | Locustのサマリーやログは軽量で、1回数MB程度なら無料枠内の想定だった |

見ての通り、**どのサービスも「想定通りに動けば」無料枠に収まる設計**でした。GitHub Actions自体は試験の完了を待機せずLambdaを呼び出すだけなので、GHAの実行時間は数十秒程度で想定通り。誤算だったのは、そのLambdaが叩くLocustの負荷試験側で、DEBUGログを絞らないまま100人分の座標データを毎秒吐き出させてしまったことでした。想定していた「軽いログ」が、想定外の量に化けてCloudWatch Logsの取り込み料金を直撃したというわけです。

システムの設計時に見ていたのは「このアーキテクチャなら課金されないはず」という各サービスの料金表だけで、**そのシステムの上で動かすアプリが何をどれだけログに吐くか、という視点が抜けていました**。ここが今回の一番の反省点です。

## どう解決したか

これ以上のコスト爆発を防ぐため、そして今後の再発を防止するために、以下の対策を打ちました。

### 1. ログレベルの適正化（Socket.ioログの除外）
一番の原因であるログ出力を絞りました。
環境変数等でログレベルを制御できるようにし、デフォルトの `info` レベルではSocket.ioの細かい通信ログ（ペイロードなど）は出力しないようにアプリケーション側のロガー設定を修正しました。

### 2. CloudWatch Logsの保持期間（Retention Period）を設定
これもの「AWSあるある」ですが、CloudWatch Logsの保持期間はデフォルトで「失効しない（無期限）」になっています。
塵も積もればストレージ料金として効いてくるため、開発・検証環境のロググループは保持期間を「1ヶ月」などに設定し、不要な古いログが自動で消えるようにライフサイクルを見直しました。ちなみに2年前くらいから蓄積されてましたが、これよりもずーーとログの取り込みのコストの方が高かったです。

### 3. CI/CD（CodeBuild）の不要なCloudWatch出力を無効化
ついでに他の無駄も削ぎ落としました。
GitHub Actionsから呼び出しているAWS CodeBuildのビルドログがCloudWatchに出力されていましたが、GitHub Actions側のコンソールで十分確認できるため、CodeBuild側のCloudWatch出力設定を無効化しました。

## ルート分岐：TrueEnd / BadEnd

あの日、あのときこうしていれば……実はTrueEndに行けていた。何が悪かったのか振り返ります。

```
負荷試験システムを作成
　⇩
後輩のYさんに負荷試験を依頼
　⇩
　→ ifルート：DEBUGログをオフにして実行 → コスト増なし　TrueEnd
　⇩
DEBUGログのまま100人規模で負荷試験を実行
　⇩
ローカルではログ量に気づかずPCが固まる程度で放置
　⇩
　→ ifルート：Billing権限があり自分でコスト監視 → 数百円で気づいて破産回避　TrueEnd2
　⇩
Billing権限がなくコストの異変に気づけない
　⇩
数日後、先方のCost Explorerでグラフが「そびえ立つ青い塔」化
　⇩
クラウド破産(Now!!)
```

つまり、以下のいずれかをやっていれば防げていた問題でした。

1. **負荷試験前にログレベルを`DEBUG`から`info`へ落とす**
2. **自分にもBilling/コスト閲覧権限を持たせておく**

システムの料金表だけを見て「このアーキテクチャなら課金されないはず」と安心していたのが一番の敗因でした。実際に動かすアプリがどれだけログを吐くか、そして自分がその異変にすぐ気づける権限を持っているか。この2つがどちらも欠けていたのが、クラウド破産一歩手前まで進んでしまった理由です。

## まとめと後日談

今回の件で、CloudWatch Logsの取り込み料金は意外と高くつくということを身をもって学びました。

これからLocustやk6などで負荷試験を実施しようとしている方は、実行ボタンを押す前に**ログレベルがDEBUGになっていないか？**をぜひ一度確認してみてください。

ちなみに後日談として、自分たちでもコストの異常に気づけるようにしたいと相談した結果、**無事に私にもAWSのコスト閲覧権限が付与されました。** これからは、開発だけでなくコスト意識もしっかり持ちながら運用していこうと思います。

私のこのヒヤッとした経験が、誰かのクラウド破産を未然に防ぐ参考になれば幸いです！
